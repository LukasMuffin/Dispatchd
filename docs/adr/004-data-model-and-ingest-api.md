# ADR-004: Data model and ingest API

- **Status:** Proposed
- **Date:** 2026-10-13

## Context

Milestone 1 needs the first tables and the first real API: tenants register the
endpoints they want events sent to, then submit events, and the worker delivers
each event to each endpoint.

ADR-001 settles part of the shape. Deliveries are the jobs: one row per event per
endpoint, written in the same transaction as the event, which is what keeps
enqueueing atomic. So fan-out happens at ingest time, and an endpoint registered
after an event was accepted doesn't receive that event.

Two questions are still open:

1. **How a request identifies its tenant before API keys exist.** API keys are
   milestone 3. Until then the API needs some way to know which tenant an event or
   endpoint belongs to, and that choice affects whether the URLs change in
   milestone 3.
2. **Which of a tenant's endpoints receive an event:** all of them, or only those
   subscribed to its event type.

The sketch below is the proposed starting point that both decisions build on. It's
open to change too.

### Proposed schema

| Table | Columns |
|---|---|
| `tenants` | `id`, `name`, `created_at` |
| `endpoints` | `id`, `tenant_id`, `url`, `created_at` |
| `events` | `id`, `tenant_id`, `type`, `payload` (`jsonb`), `created_at` |
| `deliveries` | `id`, `event_id`, `endpoint_id`, `status`, `attempts`, `next_attempt_at`, `last_error`, `created_at`, `updated_at` |

- IDs are UUIDs generated by Postgres (`gen_random_uuid()`), so they can appear in
  URLs and responses without revealing how many rows exist.
- `deliveries.status` is `pending`, `succeeded`, or `failed`. Milestone 2 adds
  retries and a `dead` status.
- `deliveries` has a unique constraint on `(event_id, endpoint_id)` and a partial
  index on `next_attempt_at WHERE status = 'pending'`, which is what the worker's
  `SKIP LOCKED` query scans.
- Lease columns for claiming work come from the worker semantics ADR. The
  idempotency key on `events` comes in milestone 2.

### Proposed API shape

- `POST .../endpoints` with `{"url": "https://..."}` → `201` with the endpoint.
  Only `http` and `https` URLs are accepted.
- `GET .../endpoints` → the tenant's endpoints.
- `POST .../events` with `{"type": "order.created", "payload": {...}}` → `202
  Accepted` with `{"id": ..., "type": ..., "created_at": ...}`. `202` because
  delivery happens later. The payload must be a JSON object, with a size limit
  (for example 256 KB) so one tenant can't store arbitrarily large rows.

What the `...` is depends on decision 1.

## Decision 1: How requests identify the tenant (until milestone 3)

### Option A: Tenant ID in the URL path

`POST /tenants/{tenant_id}/events`, `POST /tenants/{tenant_id}/endpoints`, and an
unauthenticated `POST /tenants` to create tenants in milestone 1.

- **Pros:**
  - Explicit and easy to try with curl or the FastAPI docs page.
  - Ordinary REST nesting that reviewers will recognize.
- **Cons:**
  - Anyone can act as any tenant until milestone 3. Fine locally, but not
    deployable.
  - In milestone 3 the API key already says which tenant is calling, so the path
    segment becomes redundant. We'd either change every URL (a breaking change) or
    keep it and check that it matches the key.

### Option B: Tenant ID in a header

`POST /events` and `POST /endpoints` with an `X-Tenant-ID` header, plus an
unauthenticated `POST /tenants` in milestone 1.

- **Pros:**
  - URLs already have their final shape. In milestone 3 the header is replaced by
    `Authorization: Bearer <key>`, and the routes don't change.
  - The dependency that resolves the tenant becomes the single place where API key
    auth plugs in later.
- **Cons:**
  - Same lack of authentication as Option A until milestone 3.
  - A custom header is a little less discoverable than a path parameter, though
    the FastAPI docs page still shows it.
  - The header is temporary and gets removed in milestone 3.

### Option C: Minimal API keys now

Each tenant gets an API key when created. Requests send `Authorization: Bearer
<key>`, and the API looks up the tenant from a hash of the key.

- **Pros:**
  - The final contract from day one, with no temporary mechanism to remove later.
  - Safe to deploy as soon as milestone 1 is done.
- **Cons:**
  - Pulls milestone 3 work into milestone 1 and makes its PRs bigger.
  - Key format, hashing, and rotation are milestone 3 decisions that would be made
    early, before HMAC signing is designed alongside them.
  - Every test and manual request needs a key first.

## Decision 2: Which endpoints receive an event

### Option X: Every endpoint of the tenant

- **Pros:** simplest model and query. Nothing to configure.
- **Cons:** receivers get every event type and have to filter on their side.
  Adding filtering later needs a migration and an API change.

### Option Y: Endpoints can subscribe to event types

`endpoints` gets an `event_types` column (`text[]`). Empty or null means all types.

- **Pros:** matches how hosted webhook services usually work. Receivers only get
  what they asked for.
- **Cons:** more to build and test in milestone 1: validation, the fan-out query,
  and the API fields. Type matching rules (exact match only, or wildcards like
  `order.*`) are one more thing to decide.

## Comparison

| | A: Path | B: Header | C: API keys now |
|---|---|---|---|
| Milestone 1 effort | Low | Low | Medium |
| URLs change in milestone 3 | Yes, or redundant check | No | No |
| Safe to deploy after milestone 1 | No | No | Yes |
| Temporary code to remove | Path segment | Header dependency | None |

## Questions that would decide this

- Do you want the milestone 1 build to be deployable, or is local-only fine until
  milestone 3?
- Should the URLs stay stable across milestones, or is a breaking change in
  milestone 3 acceptable?
- Is event-type filtering part of what you want to show in milestone 1, or can it
  wait?
